Who can do what, and where each rule is enforced.

- Three layers gate a request; only the server-action layer is authoritative.
- The matrix is code: `ROLE_CONFIG`, `CAPTAIN_PERMISSIONS` in
  `src/utils/permissions.ts`.
- The table below is rendered from it, so it cannot drift.

## Auth layers

<Tabs items={['1. Proxy', '2. withResource', '3. Client']}>
<Tab value="1. Proxy">

`src/proxy.ts` runs on page navigations only.

- **Skipped:** server actions (`next-action` header) pass through.
- **Excluded by matcher:** `/api`, `/llms*`, static assets.
- **`/docs/*`:** public; only gets the language rewrite.

Redirects:

- **No session cookie** (`getSessionCookie`, prefix `sgr`) on a protected
  route → `/login`.
- **Cookie on** `/`, `/login`, `/forgot-password`, `/new-password` →
  `/dashboard`.
- **Cookie but `getCookieCache` empty** (1-hour cache expired) → `/login`.
- **`can(role, resource, 'view')` fails** → `/forbidden`. Resource comes from
  the path prefix (`/periodic-testing/add-result` → `periodic-testing`).
- Only `view` is checked, by role only; Captain adds no `view` grant.

</Tab>
<Tab value="2. withResource">

`src/actions/auth.ts`. The only layer that cannot be bypassed.

- **`verifySession()`:** React-`cache`d `auth.api.getSession`; once per
  request.
- **`withAuth(fn)`:** no session → `/login`; injects `session.user` as first
  arg. Reads use it directly.
- **`withResource(resource)(actions, fn)`:** wraps `withAuth`, builds
  `defineAbility(user.role, user.is_captain)`.
- Calls `forbidden()` unless `canAll` holds for every listed action.

```ts
const roster = withResource('roster');
export const addUser = roster(['create'], async (user, values) => { ... });
```

This authorizes a resource, not a record. See [Ownership checks](#ownership-checks).

</Tab>
<Tab value="3. Client">

UX only; never trusted.

- **Session:** the protected layout passes only `session.user` to
  `SessionProvider`; the token never reaches the client.
- **Freshness:** `authClient.useSession()` keeps it fresh afterwards.
- **`usePermissions`:** derives the same `Ability` from that user.
- **`Authorized`:** renders `children` only when the check passes; `fallback`,
  `loading` slots, `mode="all" | "any"`.
- **`Visibility`:** plain show/hide around React `Activity`; knows no roles.

```tsx
<Authorized resource="roster" action="create">
  <AddButton />
</Authorized>
```

</Tab>
</Tabs>

## Ownership checks

- The matrix gates a resource, never a specific row.
- Where the row matters, the action compares it with the injected `user`.
- Mismatch → `forbidden()`. Rules in code today:

Patterns that generalise:

- **Never trust payload identifiers.** `team_id` always comes from the session.
- **`role` is privileged.** Only SUPER_ADMIN may change it.
- **Prefixes are not ownership.**
- **Narrow reads.** `getRoster` selects only the columns the table shows.
