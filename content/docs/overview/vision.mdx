title: Vision
description: The problem the portal replaces, the vision, and what is deliberately out of scope.

## Problem

Club operations lived in spreadsheets and group chats:

- **Stale information.** No single up-to-date copy.
- **Unclear ownership.** No one clearly owned each workflow.
- **No cross-role visibility.** Coaches couldn't see who had excused
  themselves; players had to ask for the next session.

## Vision

One private, role-based hub: the club's single source of truth.

- Any member answers "who, when, where" in seconds.
- Each workflow owner (attendance, registration, testing) runs it end to end
  without leaving the app.

## Non-goals

Not planned without a new product signal; the code assumes one trusted club.

- **Multi-club or public product.** One `team` row is `is_default`; opponents
  are lightweight `team` records, not tenants.
- **Self-service sign-up.** No register page. Admins or captains add accounts
  from Roster (`addUser`); a password-reset email activates them.
- **Injury tracking, payments, audit logs.** Only on real demand.
- **Native mobile apps.** Responsive web only.

## Constraints

- **Trusted members.** All invited; the server still enforces every
  permission (see [Principles](/docs/overview/principles)).
- **Small, static role set.** `UserRole`: `GUEST`, `PLAYER`, `COACH`,
  `SUPER_ADMIN`, plus `player.is_captain`. Permissions are code (`ROLE_CONFIG`).
- **Tens of users, not thousands.** One club, one default team; performance
  and pagination are sized for that.
- **Better Auth sessions.** Email + password only; 1-hour session, signed
  cookie cache; no OAuth.
