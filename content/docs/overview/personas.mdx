- **Role:** Postgres enum `user_role` on `user.role`.
- **Captain flag:** `player.is_captain`.
- Both come from the session; `defineAbility(role, isCaptain)` builds an `Ability`.
- Each persona maps to one row or column of the
  [permission matrix](/docs/access/roles-permissions).

## How the roles differ in code

- **Captain is additive.** `can()` checks `ROLE_CONFIG[role]`, then
  `CAPTAIN_PERMISSIONS` only if `role === PLAYER && isCaptain`.
- **No other role gains from the flag**, and a captain keeps every PLAYER right.
- **GUEST has no `profile` permission.** `getUserProfile` calls `forbidden()`
  before reading any record.
- **SUPER_ADMIN is computed.** Every `RESOURCES` entry maps to `ALL_ACTIONS`;
  a new resource is admin-only until granted to another role.
- **Row ownership is separate from role.** The action checks own attendance and
  profile against the session user, not the matrix
  ([ownership checks](/docs/access/roles-permissions#ownership-checks)).

<Callout type="info" title="Trusted but still gated">
  The UI only hides controls. Every server action re-checks role and, where
  relevant, ownership.
</Callout>
