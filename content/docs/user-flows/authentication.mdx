> Grounded in [Roles & Permissions](/docs/access/roles-permissions). There is no
> self-service sign-up: accounts are provisioned by an admin or captain, and the
> member activates the account through a password-reset email.

## Request gating (every page navigation)

Three layers gate every request; only the server-action layer is authoritative.

<Mermaid
  chart={`
flowchart TD
    A[Page navigation] --> B{Session cookie present<br/>and cache fresh?}
    B -- no --> L[Redirect to /login]
    B -- yes --> C{"can(role, resource, 'view')"}
    C -- denied --> F[Redirect to /forbidden]
    C -- allowed --> P[Render page]
    P --> D[User triggers a server action]
    D --> E{withAuth / withResource:<br/>role allows all listed actions?}
    E -- no --> X[forbidden]
    E -- yes --> O{Ownership check<br/>where the record matters}
    O -- mismatch --> X
    O -- ok --> S[Action runs]
`}
/>

- **Layer 1 — proxy** (`src/proxy.ts`): cookie presence + view-permission gate on page navigations; it does not run for server actions.
- **Layer 2 — `withAuth` / `withResource`**: the only layer that cannot be bypassed; runs inside every server action, plus per-record ownership re-checks.
- **Layer 3 — client session**: hides UI affordances only; never trusted for security.
