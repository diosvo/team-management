## Purpose

- Records each player's score on the club's own tests (sprint, jump, …) by date.
- Main page: one testing day as a player × test-type matrix.
- Sub-routes: enter a whole session at once; maintain the test-type catalogue;
  track progression per team and per player, with coach notes and goals.

## Access

<PermissionMatrix resource="periodic-testing" />

- PLAYER only views.
- COACH, SUPER_ADMIN and captains hold every action: **Add Result**, **Manage
  Types**, inline cell edits, row selection on test types.
- Cell editability uses `can('periodic-testing', 'edit')`, as the server does.

## Flows

<Tabs items={['Matrix', 'Add result', 'Test types']}>
  <Tab value="Matrix">

    - Rows are players; columns are test types with a result that day, headed
      `Name (unit)`.
    - The date select lists `getTestDates()`; no date gives an empty matrix.
    - Only a date change reloads the server (`shallow: false`); it resets
      `type` and `page`.
    - `q`, `type` and `page` are client-only. 10 players per page.
    - Each cell is a Chakra `Editable` number input:
      - Empty cell → `createTestResult` with one row.
      - Filled cell → `updateTestResultById`; cleared → `deleteTestResultById`.
      - Unchanged value or clearing an empty cell writes nothing.
      - A failed write reverts the draft.

  </Tab>
  <Tab value="Add result">

    - Guarded by `canCreateTestResult()` on the server; fails → `forbidden()`.
    - Step 1: active players, up to five test types, a date (default today).
    - Step 2: a players × types grid of number inputs.
    - Clicking a column header or player name drops it from the selection.
    - Blank cells submit as `0`.
    - On success, redirects to `/periodic-testing?date=<date>`.

  </Tab>
  <Tab value="Test types">

    - `/test-types` lists the team's types with search and a unit filter.
    - **+ Add** and row click open the same dialog: name, one unit,
      direction (higher or lower is better) and an optional target.
    - Units: `meters`, `percent`, `points`, `reps`, `seconds`, `times`.
    - Form defaults to `seconds`; the column defaults to `times`.
    - Selected rows delete in bulk; a type that still has results is refused.

  </Tab>
</Tabs>

## Progression

<Tabs items={['Team', 'Player', 'Notes & goals']}>
  <Tab value="Team">

    - `/periodic-testing/progression`, linked from the testing header.
    - One test type at a time; `type` empty → first type with results.
    - Stats: team average and best (from each player's latest result) and
      players who missed the latest test.
    - Table per player: baseline, latest, best, change, status, band.
    - Filters: `status` and `band` (client-only); only a `type` change
      reloads the server.

  </Tab>
  <Tab value="Player">

    - `/periodic-testing/progression/[id]`, opened from a player name in the
      matrix.
    - Stats: tests tracked, improving, regressing, on target (elite or on
      target).
    - One card per tested type with a chart against the team average, then
      test history and notes.

  </Tab>
  <Tab value="Notes & goals">

    - A note is a coach's observation, optionally tied to a test type (its
      focus area), with an optional `goal` for the next test.
    - One note per player and type: saving a typed note updates the existing
      one. General notes (no type) can be many.
    - A goal is judged by the first result after the note: **met**,
      **missed**, or **pending** until the player is tested again.
    - Edit and delete buttons follow `can('periodic-testing', 'edit' |
      'delete')`.

  </Tab>
</Tabs>

### Status and band

- **Change** is baseline → latest, signed so positive always means better
  (a faster sprint is positive).
- **Status** compares the last tests with a 2% noise threshold:
  - `improving` / `regressing`: the latest test moved past it.
  - `plateauing`: neither of the last two tests moved past it.
  - `stable`: only the latest held steady.
  - `insufficient`: fewer than two results.
- **Band** places the latest result against the type's `target` with a 10%
  margin: `elite`, `on_target`, `below_target`, `needs_work`. No target → no
  band.

## Rules

- **One result per player, test type and date.** `createTestResult` upserts
  on that triple:
  - `getExistingTestResults` resolves the batch in one `IN`-filtered query.
  - Rows are re-checked against the submitted keys (the filters cross-product).
  - One insert for new cells, one update pass for existing ones.
  - Toast: `{N} created, {M} updated`.
- **Unique type names per team.** Unique index `team_test_type_name` on
  `(team_id, name)`; 3–64 characters.
- **A type in use cannot be deleted.** `test_result.type_id` is
  `onDelete: 'restrict'`; `removeTestType` maps
  `test_result_type_id_test_type_type_id_fk` to “Type is being in use.”
- **Notes stay inside the team.** `test_note` has no `team_id`; every note
  write checks the player is on the team or was tested by it, and updates and
  deletes are scoped by `player_id` as well as `note_id`.
- **A deleted type keeps its notes.** `test_note.type_id` is
  `onDelete: 'set null'`, so the note becomes a general note.
- **Revalidation.** Results → `/periodic-testing`; types →
  `/periodic-testing/test-types`; notes → the player's progression page.

### Progression

- Server actions in `src/actions/progression.ts`, all behind
  `withResource('periodic-testing')`.
- `test_note` has no `team_id`, so note writes call
  `isPlayerInTeamScope(team_id, player_id)` first: the player is on the
  caller's team now, or the team has a result for them. Otherwise the action
  returns “Note not found”.

## Acceptance

<Accordions>
  <Accordion title="A player sees the matrix without controls">
    A non-captain PLAYER sees the matrix, stats and date select only. No **Add
    Result** / **Manage Types**; cells do not open an input.
  </Accordion>
  <Accordion title="Re-submitting a session updates rather than duplicates">
    A second identical submit reports `0 created, N updated`; one value per
    cell.
  </Accordion>
  <Accordion title="A type with results cannot be deleted">
    Fails with “Type is being in use.”; the type stays listed.
  </Accordion>
  <Accordion title="A typed note is one per focus area">
    Saving a second note for the same player and type updates the first; toast
    “Note updated successfully”.
  </Accordion>
  <Accordion title="Notes cannot reach another team's players">
    `saveTestNote` or `removeTestNote` for a player outside the caller's team
    fails with “Note not found” and writes nothing.
  </Accordion>
</Accordions>
